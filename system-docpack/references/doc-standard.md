# System Docpack Standard

Canonical contract for the per-system document pack (docpack) used across the
Solo Empire portfolio. EV3 (`bookchaowalit-freelance/oak/ev3-franchise/EV3-DOCPACK-v0.1`) is
the reference implementation; this standard is the portable subset every
system must meet for its tier. The machine-readable copy of the doc types and
tiers lives in `repository-catalog/registries/docpack-coverage.yaml`; keep
both in sync.

## Tiers

| Tier | Use for | Required doc types |
|---|---|---|
| L0 Card | Every personal Book Dev repository by default | product-card |
| L1 Lite | Internal tools and single-owner apps | overview, prd, architecture, nfr-security, runbook |
| L2 Standard | Our public website and small client/internal systems | L1 + srs, ux-flows, test-uat, rtm |
| L3 Full | Paid client systems with acceptance or handover | L2 + business-case, business-flow, business-rules-data, trd-api-data, delivery-raid, decisions-glossary |

Personal repositories in the book-dev GitHub checkout
are discovered automatically and always need a `product-card`; a repository
whose card verdict is `invest` is promoted to L1+ through `tier_overrides` in
the registry. A system may exceed its tier. Do not inflate a tier with placeholder text: a
short document grounded in evidence beats a long invented one.

## Pack layout

```text
<system-root>/DOCPACK/
├── docpack.yaml          # brand, prefix, tier, audience
├── 00-overview.md
├── 01-prd.md
├── ...                   # NN-<doc_type>.md, numbered in the order below
└── pdf/                  # generated by `task docpack:build -- <system-id>`
```

Legacy packs (EV3, TMA) keep their file names; the registry maps each doc type
to its file instead.

`docpack.yaml`:

```yaml
system_id: scan-n-pop          # must match the registry id
prefix: SNP                    # doc_id prefix, e.g. SNP-DOC-01
brand: "SCAN-N-POP"            # cover kicker (uppercase, short)
subtitle: "แพลตฟอร์ม ... "      # one-line Thai description on the cover
footer: "Scan-n-pop — ฉบับร่างเพื่อพิจารณา"
color: "#1f4e79"               # brand colour (hex)
audience: client               # client | internal
tier: L3
```

## Product Card (L0)

`DOCPACK/00-product-card.md`, one page, answers "is this a product with value,
and what happens next?" Write it from `infra/scripts/docpack/repo_facts.py`
output plus the README and code. Extra front matter: `verdict:` (below),
`doc_id: CARD-<repo-name>`, `doc_type: product-card`.

Required sections:

1. สรุปคุณค่าในหนึ่งประโยค — who it helps and with what outcome.
2. ปัญหาและผู้ใช้เป้าหมาย
3. สิ่งที่ทำได้จริงตอนนี้ — features verified in code, not the README's wishes.
4. หลักฐานสถานะ — stack, commits, first/last commit, tests, CI, deploy
   config, live URL (checked facts only).
5. คุณค่าและจุดต่าง — why someone would use it over alternatives; any
   revenue or reuse angle marked **[สมมติฐาน]**.
6. ช่องว่างสำคัญ — what blocks it from being a real product.
7. คำตัดสิน — verdict, reason, and the condition that would change it.
8. ขั้นต่อไป — 1-3 concrete next actions.

| verdict | Meaning | Follow-up |
|---|---|---|
| invest | Real problem, working core, worth continuing | Promote to L1 (or higher) docpack |
| showcase | Good portfolio evidence, not a business | Keep README/demo honest and current |
| template | Starter or scaffold for new products | Label as template; no product claims |
| merge | Duplicates another repo | Name the canonical twin |
| archive | No meaningful value left | Archive after owner approval |

## Front matter (every document)

```yaml
---
title: <System> — <Document name>
doc_id: <PREFIX>-DOC-<NN>
doc_type: <one of the doc types below>
version: 0.1
date: YYYY-MM-DD
status: ร่างเพื่อพิจารณา
owner: <role, never a private person's contact detail>
related: <comma-separated sibling file names>
---
```

## Writing rules

- Thai body text; keep code, paths, identifiers, API names, and standard
  acronyms (PRD, SRS, NFR, UAT, RTM, ADR) in their original form.
- Evidence first. Every fact must come from the repository (code, configs,
  notes, minutes, existing docs). Cite internal sources in a final
  `## แหล่งข้อมูล` section; the PDF builder strips that section and
  `แหล่ง`/`Source` table columns from the client edition.
- Unknowns are labelled, never invented: **[ต้องยืนยัน]** for a fact that an
  owner must confirm, **[สมมติฐาน]** for a working assumption.
- Never include secrets, credentials, tokens, personal contact data, raw
  customer data, or private transcripts. Use role names, not personal names,
  for client-side people.
- Use mermaid (` ```mermaid `) for flows, sequences, state machines, ER
  diagrams, and gantt charts; the builder renders them.
- IDs are stable and cross-referenced: `FR-xx` (functional), `NFR-xx`,
  `BR-xx` (business rule), `UC-xx`/`US-xx`, `TC-xx` (test), `ADR-xx`,
  `D-xx` (decision), `Q-xx` (open question), `R-xx` (risk).

## Doc types and required sections

| # | doc_type | Name | Owner role | Required sections |
|---|---|---|---|---|
| 00 | overview | ภาพรวมระบบและสารบัญเอกสาร | Product | สรุประบบ 1 ย่อหน้า, สถานะปัจจุบัน, ผู้ใช้หลัก, ตารางรายการเอกสาร (รหัส/ชื่อ/ผู้อ่าน), วิธีอ่าน |
| 01 | prd | Product Requirements (PRD) | Product | ปัญหาและเป้าหมาย, ผู้ใช้/persona, ขอบเขต in/out, ฟีเจอร์หลักพร้อมลำดับความสำคัญ, ตัวชี้วัดความสำเร็จ, roadmap/phase, ข้อสมมติฐานและความเสี่ยง |
| 02 | architecture | System Architecture (SA) | Solution Architect | architecture style + เหตุผล, quality-attribute scenarios, context diagram, components/containers, tech stack, data stores, integrations, deployment topology, ADR สำคัญ, fitness functions, ตารางเอกสารลงรายละเอียด phase 07 |
| 03 | nfr-security | NFR และความปลอดภัย | Solution Architect + Security | performance, availability, scalability, security controls, privacy/PDPA, observability, backup/DR, เป้าหมายที่วัดได้ต่อ NFR-xx |
| 04 | runbook | Runbook การติดตั้งและดูแลระบบ | DevOps | environments, วิธี build/deploy, config/secret (ชื่อตัวแปรเท่านั้น), health check, rollback, incident/troubleshooting, backup/restore |
| 05 | srs | Software Requirements (SRS/FRD) | BA | บทบาทและสิทธิ์, use case/user story พร้อม acceptance criteria, FR-xx table (priority, phase, สถานะ) |
| 06 | ux-flows | User Flow และ Screen Inventory | UX/UI | รายการหน้าจอ (ID, ชื่อ, บทบาท, สถานะ), user flow หลัก (mermaid), หลัก design system/component ที่ใช้ |
| 07 | test-uat | Test Strategy และ UAT | QA | ระดับการทดสอบ (unit/integration/E2E/UAT), สภาพแวดล้อม, test cases TC-xx พร้อมผลคาดหวัง, เกณฑ์ผ่าน/entry-exit, หลักฐานที่มี |
| 08 | rtm | Requirements Traceability Matrix | BA + QA | ตาราง FR ↔ UC/US ↔ หน้าจอ ↔ TC ↔ สถานะหลักฐาน, ช่องว่างที่ยังไม่ครอบคลุม |
| 09 | business-case | Business Case และผู้มีส่วนได้ส่วนเสีย | BA + Product | วัตถุประสงค์ธุรกิจ, ประโยชน์ที่วัดได้, ทางเลือก, stakeholder map/RACI, governance |
| 10 | business-flow | Business Flow / Journey | BA | value chain, swimlane flows (mermaid), journey/service blueprint หลัก, จุดผิดปกติ |
| 11 | business-rules-data | กฎธุรกิจและข้อมูล | BA + Data | BR-xx table, state machines, decision tables, data dictionary/entity หลัก, data classification |
| 12 | trd-api-data | TRD: API และ Data Model | Solution Architect | ER diagram, ตาราง/entity, API endpoints (method, path, auth, หน้าที่), integration contracts, sequence diagrams |
| 13 | delivery-raid | แผนส่งมอบและ RAID | Delivery/PM | phase/milestone (gantt), deliverables, acceptance per phase, RAID log (R-xx, assumptions, issues, dependencies) |
| 14 | decisions-glossary | Decision Log, คำถามค้าง และอภิธานศัพท์ | BA | D-xx decisions, Q-xx open questions พร้อมผู้ตัดสิน, glossary |

Every document ends with `## การอนุมัติ` (role, status, date, sign-off
placeholder) before `## แหล่งข้อมูล`.

## Technical design detail documents (SDLC phase 07)

The docpack doc types above summarise a system; the technical depth behind
`architecture`, `nfr-security`, `runbook`, and `trd-api-data` lives in these
architecture-docs templates. They are SDLC artifacts, not docpack doc types:
`task docpack:check` does not require them and the registry tiers do not
change. Keep the copies in the project's SDLC workspace (or next to the pack
for systems without one) and link each from the `02-architecture` detail
section (path + version) or mark it `not_applicable` with a reason.

Which rule applies:

- **Work started on or after 2026-10-16** follows the SDLC index
  (architecture-docs `templates/sdlc/README.md`): every template below is
  required for every piece of work regardless of tier. A topic that does not
  apply is written as `N/A` + reason inside the document and passes AI review;
  small work may keep a template short or combine files, but every heading
  stays. The "Expected for" column does not waive anything for this work.
- **Existing systems with no new work since 2026-10-16** keep their docpack
  tier. Use the "Expected for" column only as the gap check for them. L0
  (product card only) needs none of these documents.
- The landscape is one file per portfolio: check that the system has a
  current row there, not a per-system file.

| Template (architecture-docs `templates/`) | Covers | Linked from | Expected for |
|---|---|---|---|
| `sdlc/infrastructure-and-network-design.md` | environments, request path, DNS, TLS, edge/WAF/CDN, network boundaries, compute and runtime, storage, scaling/HA, IaC and drift, live verification | architecture (deployment), runbook | L2+, and any L1 system with production users |
| `sdlc/observability-design.md` | SLIs/SLOs, log schema, metrics, traces and correlation IDs, dashboards, alert catalog mapped to runbook sections | nfr-security (reliability), runbook (monitoring) | L1+ in production; a system with no production deployment records `N/A` + reason |
| `sdlc/capacity-performance-and-cost-plan.md` | workload model, performance budgets, bottlenecks, load/stress/spike/soak tests, capacity forecast, cost model, unit economics, budget alerts | nfr-security (performance), business-case | L2+ |
| `sdlc/failure-mode-analysis.md` | FMEA, dependency failures, SPOFs, resilience patterns, degraded modes, data-correctness failures, game days | nfr-security (reliability), trd-api-data (execution semantics) | L2+ |
| `sdlc/async-integration-contract.md` | events, queues, webhooks, streams, scheduled jobs and workers: schema, ordering, delivery, idempotency, retry, DLQ, outbox/saga, versioning | trd-api-data | any tier that has async work; otherwise `N/A` + reason |
| `sdlc/frontend-architecture.md` | rendering per route, state, session/token storage, frontend security, Core Web Vitals, accessibility, i18n, tests | architecture, ux-flows | any tier with a UI; otherwise `N/A` + reason |
| `sdlc/tech-debt-register.md` | known debt with cause, interest, risk, repayment plan, dependency/runtime currency | overview (status), decisions-glossary | L1+ |
| `operations/system-landscape.md` | portfolio map: capabilities, owners, lifecycle, shared services, cross-system dependencies, data flows, vendors | architecture (review section) | one per portfolio; each L1+ system has a current row |
| `development-cycle/vendor-dependency-review.md` § Lock-in and exit plan | lock-in level, data export test, exit effort and trigger | architecture (ADR), delivery-raid | every paid or production-critical vendor |

`02-architecture` itself also carries architecture style and rationale,
quality-attribute scenarios, a component view (C4 level 3), and architecture
fitness functions. New SDLC work fills them (or `N/A` + reason per heading);
for existing systems they are expected at L2+ and may be `not_applicable`
with a reason at L1.

## Quality gate

`task docpack:check` must report the system as complete for its tier: every
required doc type present, front matter valid (`doc_id`, `doc_type`, `title`,
`version`, `status`), and a PDF newer than its Markdown source when the pack
has been built. Review content against the role skills:
`product-management`, `solution-architecture`, `qa-testing`,
`business-analysis`, and `security-and-privacy`.
